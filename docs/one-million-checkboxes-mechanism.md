# 仕組みの解説: 描画と省力化の観点から

> 注記: 出典は同じディレクトリの `one-million-checkboxes.md`（添付の調査レポート）です。
> 「Ironmate への当てはめ」は、この文書での整理です。Ironmate の実装が同じ仕組みだという意味ではありません。
> 描画の観点（寸法の固定、見えている部分だけを描く）は、ドット絵の話（#79 の系統）として分けています。#80・#114 とは別の論点です。

## 1. 状態は「位置」ではなく「番号」で持つ

- 100 万個のチェックボックスは、1 個 1 ビットで表せます。全体で 1,000,000 bit ＝ 125,000 byte（約 125KB）です。
- サーバーは「何番目が ON か」だけを扱います。行と列の位置は、表示する側で番号から計算します。
- 効果: 画面幅を変えても、保存している状態は変わりません。

**Ironmate への当てはめ（整理）**: 1 セル 1 ビットの見積もりは、取り込みの容量を決めるときの参考になります（#114 の上限の決め方に近い観点です）。

## 2. 描画は「見えている分だけ」にする（仮想化）

- 100 万個の DOM をそのまま作るとブラウザが止まります。
- 画面に入る数百〜数千個だけを描き、スクロールに合わせて中身を入れ替えます（レポートでは react-window を使用）。

**ドット絵の話（#79 の系統、#80・#114 とは別）**: 大きい絵は、見えている部分だけを描けば、全体を毎回描き直す必要がなくなります。これは描画の観点で、取り込みや PPTX の論点ではありません。

## 3. 変更だけを送る（差分配信とまとめ送信）

- 最初の設計は、全状態を 30 秒ごとに全クライアントへ送っていました。接続が増えると、帯域が一気に膨らみました。
- 変更を 100ms 程度の時間窓でまとめ、変わったインデックスの一覧だけを送るように変えました（マイクロバッチ）。

**Ironmate への当てはめ（整理）**: PPTX の属性置換は、全体を書き直すのではなく、変わった項目だけを置き換える、という考え方になります（#80 の議論に近い観点です）。プレビューの再描画を差分にするかどうかは、ドット絵の話として別に扱います。

## 4. 幅に依存する描画は、端末ごとに崩れる

- 画面幅で折り返す設計のため、2 次元の絵は端末によって崩れて見えます。
- 参加者は「幅 1000」を標準規格として決め、その規格の中で絵を描きました。

**ドット絵の話（#79 の系統、#80・#114 とは別）**: 出力の寸法を固定して、描画先の幅に依存させない。レポートの参加者と同じく、寸法を決め打ちするのが省力化になります。

## 5. 負荷の上限は、設計の段階で決める

- サーバー側はレートリミットを入れ、閾値を超えた操作は通しません。
- 参加者は閾値を実験で割り出し、それに合わせて操作を分散させました。

**Ironmate への当てはめ（整理）**: 外部 API や重い処理には、呼び出し上限を最初に書いておく。上限を超えた場合の扱いも決めておく。

## 6. 確認できていないこと

- 色の表現（チェックの並びを RGB として読む方法）は、コミュニティ独自の規約です。仕様として確認できていません。
- 事実は、添付レポートの記述に基づいています。実装の細部は、ソースコードで確かめていません。
- ドット絵への当てはめは、描画の観点の整理です。`pixel_grid.py` の実装が同じ仕組みだという意味ではありません。
